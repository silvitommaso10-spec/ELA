# M0.3 — Framework di architecture test

- **Stato:** Implementata
- **Riferimenti spec:** §49, §50, §51, §52
- **Branch:** `claude/framework-di-architecture-test-j3ojx3`

## Obiettivo

Trasformare le regole di dipendenza di CLAUDE.md ("Architettura, non negoziabile") in un
contratto verificabile (§52): ogni regola è espressa due volte, come contratto import-linter in
`pyproject.toml` e come test in `tests/architecture/`, e ogni test dimostra di fallire quando la
regola viene violata. I moduli sono ancora vuoti: le regole passano "a vuoto" oggi e bloccano la
prima violazione domani.

## In scope

- Quattro regole di dipendenza, ognuna con contratto import-linter e test pytest:
  1. `ela.domain` importa solo stdlib e `pydantic`.
  2. `ela.ports` importa solo stdlib (`typing` incluso) e `ela.domain`.
  3. Nessun modulo sotto `src/ela/` tranne `providers/`, `infrastructure/` e `api/` importa
     `anthropic`, `openai`, `httpx`, `sqlalchemy`, `fastapi`, `typer`.
  4. `executive/`, `tasks/`, `permissions/`, `audit/` non importano `ela.providers` né
     `ela.infrastructure`.
- `tests/architecture/rules.py`: le regole come funzioni pure sull'albero sorgente (analisi
  AST, nessun import dei moduli controllati), riusabili su una copia temporanea del package.
- `tests/architecture/test_layers.py`: le regole applicate a `src/ela`; `domain.py`, `ports.py`
  e i quattro package core devono esistere.
- `tests/architecture/test_rules_detect_violations.py`: per ogni regola, una copia di `src/ela`
  in `tmp_path` con un modulo che la viola deve produrre una violazione; i casi consentiti
  (per esempio `anthropic` in `providers/`) non devono produrne.
- `tests/architecture/test_import_linter.py`: i contratti in `pyproject.toml` coprono tutti i
  package attuali di `ela` (un package nuovo non resta scoperto in silenzio) e `lint-imports`
  rompe il contratto giusto su una copia temporanea che viola la regola.
- `tests/security/test_no_secrets.py`: scansione dei file tracciati (e non ignorati) del repo
  con pattern di API key (`sk-ant-`, `AKIA`, `ghp_`, `xox*-`, `AIza`, chiavi private, …);
  fallisce se trova qualcosa. I pattern sono verificati in positivo su file temporanei con
  chiavi finte costruite a runtime.
- `docs/adr/0002-architecture-rules.md`: le regole, come sono verificate, i limiti noti.

## Out of scope

- Le regole di §52 che richiedono codice di dominio: tool senza Guardian, capability senza
  decisione, transizioni illegali dei task. Arrivano con le milestone che introducono
  quelle entità.
- Creare `src/ela/infrastructure/`: §48 non lo prevede sotto `src/ela`. Le regole lo
  trattano come package esente/vietato se e quando esisterà, senza stub.
- Sostituire `detect-secrets` (`make secrets`): il nuovo test è un secondo livello, mirato ai
  pattern noti, che gira dentro `pytest`.
- Dipendenze runtime, codice in `domain.py` o `ports.py`.

## Criteri di accettazione

- `make check` passa; `lint-imports` riporta i quattro contratti `KEPT`.
- `uv run pytest tests/architecture tests/security` è verde sul repo vuoto.
- Per ognuna delle quattro regole esiste un test che, su una copia temporanea del package con
  un modulo che la viola, ottiene una violazione dal test pytest e un contratto `BROKEN` da
  `lint-imports`.
- Aggiungere un package `src/ela/nuovo/` senza aggiornare i contratti fa fallire
  `tests/architecture/test_import_linter.py`.
- Un file con una chiave finta (per esempio `AKIA` + 16 caratteri) fa fallire lo scanner di
  `tests/security/test_no_secrets.py`; il repo attuale lo passa.

## Test previsti

- `tests/architecture/test_layers.py::test_rule_holds[...]` — ogni regola vale su `src/ela`.
- `tests/architecture/test_layers.py::test_required_modules_exist` — `domain.py`, `ports.py` e i
  package core esistono (una regola su un file assente non vale nulla).
- `tests/architecture/test_rules_detect_violations.py::test_violation_is_reported[...]` —
  ogni regola segnala il modulo che la viola (import assoluto, relativo, dentro `if
  TYPE_CHECKING` o in una funzione).
- `tests/architecture/test_rules_detect_violations.py::test_allowed_import_is_not_reported[...]`
  — i casi consentiti non producono falsi positivi.
- `tests/architecture/test_import_linter.py::test_contracts_cover_current_packages` — i
  contratti enumerano i package attuali.
- `tests/architecture/test_import_linter.py::test_lint_imports_breaks_contract[...]` —
  `lint-imports` esce con 1 e nomina il contratto rotto.
- `tests/security/test_no_secrets.py::test_repository_has_no_secrets`,
  `::test_pattern_is_detected[...]`, `::test_clean_file_has_no_findings`,
  `::test_binary_files_are_skipped`, `::test_patterns_do_not_match_their_own_source`.

## Rischi

- L'analisi è statica: un `importlib.import_module("anthropic")` non viene visto. È un limite
  accettato e documentato nell'ADR; la review resta la difesa.
- I contratti import-linter enumerano i package: la lista può invecchiare. Mitigato dal test
  che confronta i contratti con l'albero reale.
- Lo scanner di secret usa pattern noti: non trova secret senza prefisso riconoscibile;
  `detect-secrets` (entropia, keyword) copre quel caso.

## Domande aperte

- La regola 2 vieta `pydantic` in `ports.py`, alla lettera del prompt ("solo domain + stdlib +
  typing"). Se i port dovranno esporre modelli pydantic propri, la regola va allentata con un
  nuovo ADR.
